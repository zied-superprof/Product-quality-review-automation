## Step 5b: Append sub-dialogue (FEEDBACK-05)

Triggered when the user picks `append` on a conflicted item in Step 5. For each `append`-marked item:

### 5b.1 — Adaptive question gate (D-12)

Inspect the two conflicting rules (the new item and the existing rule from `corrections_log.json` / `rules_summary.json` / config). Determine, for each of the three categories, whether the answer is **obvious from the rule text** or **requires user input**:

1. **Contradictory?** — do the two rules give opposite verdicts on the same input (e.g. "always flag X" vs "never flag X")?
   - If both rules cite explicit opposite verdicts → mark "obvious: yes" — skip the question.
   - Otherwise → ask: `Are these rules contradictory, or do they cover different cases?`

2. **Different contexts?** — do the two rules apply to different positions, structures, or scopes (e.g. one inside `<TPL_LOOP_ANNONCES>`, the other in body)?
   - If rule text already references a structural position or scope → mark "obvious: yes" — skip.
   - Otherwise → ask: `Do these rules apply to different contexts (e.g. different blocks, positions, language families)? If yes, what distinguishes them?`

3. **Boundary?** — is there a line that separates rule A's domain from rule B's domain (e.g. "for languages X..."; "for variable Y..."; "in title position only")?
   - If both rules already specify scope predicates → mark "obvious: yes" — skip.
   - Otherwise → ask: `What's the boundary between the two rules — what determines which one applies?`

Ask only the categories where "obvious: yes" did NOT mark them. If all three are obvious, skip directly to 5b.2.

### 5b.2 — Self-check block (D-14)

Before drafting the merged rule, display this inline triple-check block — **always shown to the user**, even when all checks pass (transparent reasoning over hidden internal validation):

```
Self-check:
  [✓ or ⚠] Boundary explicit ([one-phrase summary of what's clear or unclear])
  [✓ or ⚠] Variable scope clear ([one-phrase summary of what's clear or unclear])
  [✓ or ⚠] Edge case: [concern phrase if any] — needs your input
```

The three rows are fixed labels: **Boundary explicit**, **Variable scope clear**, **Edge case**. Each gets a `✓` (clear) or `⚠` (needs input) marker.

**If any row is `⚠`:** ask one targeted clarifying question BEFORE drafting. Example:
- `⚠ Boundary explicit (which markets does the new rule apply to?)` → ask: `Which markets exactly does this rule cover — only es_AR, or all Latin American markets?`

After user answers (or if all rows were `✓`), proceed to 5b.3.

### 5b.3 — Merged-rule preview (D-13, bilingual)

Display this exact 5-line block:

```
**Merged rule:** [one-sentence rule combining the two originals]
**Why merged:** [one line — what insight unifies them]
**Example (EN):** [example sentence in English]
**Example (FR):** [example sentence in French]
**Replaces:** rule_id_a, rule_id_b (will be archived)
```

**Bilingual example sourcing (CONTEXT.md Claude's Discretion):** if the original feedback or rule text doesn't include EN + FR examples, the agent generates them from the merged-rule semantics. The user verifies them as part of this preview block — that is the verification path (no separate confirmation step).

### 5b.4 — User clarity check

After the preview, prompt:
```
Type `clear` to confirm the merged rule, or paste corrections to any of the five lines above (`Merged rule: ...`, `Example (EN): ...`, etc).
```

If the user types `clear` → proceed to 5b.5.
If the user pastes corrections:
- Update the affected lines.
- Re-display the self-check block (5b.2) with refreshed `✓ / ⚠` markers — at least one row should now be `✓` if the correction resolved a `⚠`.
- Re-display the preview (5b.3).
- Re-prompt 5b.4. Loop until the user types `clear`.

### 5b.5 — Write the merged rule and archive originals (D-15)

On `clear`:

1. Generate a new `rule_id` for the merged rule. Format: `merge_<YYYYMMDD>_<short-hash>` (4-char hex hash of `rule_a.id + rule_b.id` is sufficient).
2. Compute the merged confidence:
   - Take `max(rule_a.confidence, rule_b.confidence)` using ordering `high > medium > low`.
   - Downgrade by one tier: `high → medium`, `medium → low`, `low → low`.
3. Trigger the Step 2 backup if not already triggered (this is a write).
4. Write the merged rule to `corrections/corrections_log.json` > `corrections` array as a new 8-field entry (same schema as Step 6, with `notification_type = NOTIFICATION_TYPE` from Step 1, `rule_extracted` set to the merged rule text, `confidence` set to the downgraded value).
5. Append both originals to `corrections/archive/rules_archive.json` > `archived` array. Each archive entry:

```json
{
  "rule_id": "<original rule_id from rules_summary.json, OR a hash of the original entry if it lived only in corrections_log.json>",
  "reason": "merged_into:<new_rule_id>",
  "archived_at": "<ISO 8601 UTC timestamp YYYY-MM-DDTHH:MM:SSZ>",
  "original_record": { ...full original record verbatim... }
}
```

6. **Do NOT delete** the originals from `corrections_log.json` directly — the rebuild in Step 7 will collapse them since the merged rule has the same `language + issue_category + semantic match` as one or both originals. The `_archive` is the audit trail; the rebuild is the dedup.

7. Acknowledge to the user:
   ```
   Item #N appended:
     New merged rule_id: <merge_id>
     Confidence: <downgraded_value> (was <max_value>)
     Archived: rule_id_a, rule_id_b → corrections/archive/rules_archive.json
   ```

After all `append` items complete, control returns to Step 5 to continue with `replace` and `dismiss` items, then Step 6 writes them, then Step 7 rebuilds rules_summary.json once.
```

|-----------|----------|-----------|-------------|-----------------|
| T-13.03-01 | Tampering | rules_archive.json corruption on concurrent append (merge + prune in same session) | mitigate | Plan 13-04's prune phase runs AFTER Plan 13-03's merge writes (Step 5b runs at Step 5/6 boundary; Step 9 prune is after Step 7 rebuild).
