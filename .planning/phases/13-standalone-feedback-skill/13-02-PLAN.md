**4. Step 2 — Backup-on-first-write convention:**
```markdown
## Step 2: Backup-on-first-write convention

When the session is about to make its **first write to disk** (and only then), back up all five writable files to `corrections/backups/`. This runs once per session, before the first write — never per-item.

```bash
TS=$(date -u +%Y%m%dT%H%M%SZ)
mkdir -p corrections/backups
for f in \
  corrections/corrections_log.json \
  corrections/rules_summary.json \
  config/label_patterns.json \
  config/tone_guidelines.json \
  config/variables_guide.md
do
  [ -f "$f" ] && cp "$f" "corrections/backups/${TS}_$(basename "$f")"
done
```

**Mid-session new destination:** if a promotion later in the session writes to a destination that wasn't backed up at session-start (rare — only happens if the promotion phase introduces a brand-new file path), back THAT specific file up at the moment of first write to it.
```

**7. Step 5 — Consolidated conflict scan + numbered list (FEEDBACK-04):**
```markdown
## Step 5: Conflict scan + consolidated numbered list (FEEDBACK-04, D-12)

For each writable item (skip Variables.csv flag-only items), run a conflict scan against:
- `corrections/corrections_log.json` — same `language` + same inferred `issue_category` + semantic similarity on `rule_extracted` (per Phase 3 D-17/D-18/D-19).
- `config/label_patterns.json` — `subject_variable_usage_rules` if the rule touches variable usage.
- `config/tone_guidelines.json` — `formality_rules` if the rule touches formality.
- `config/variables_guide.md` — the variable's H3 section if the rule touches a specific variable (per Phase 13 D-11 routing tree extension).

**What counts as a conflict** (lifted from Step 7a-single):
- New rule says "do NOT flag X for language Y" but an existing rule says "always flag X" (or vice versa).
- New rule says "use variable A for language Z" but `subject_variable_usage_rules` says use variable B.
- New rule contradicts a formality classification in `tone_guidelines.json`.

**What is NOT a conflict:**
- Rule adds guidance for a case not covered by existing rules (additive).
- Rule refines an existing rule without contradicting it.

After scanning all items, present the consolidated numbered list:

```
Batch analysis complete — [N] items parsed:

#1 — [language_code]: [brief issue summary, max 10 words]
  → Routes to: [corrections_log.json | Variables.csv (flag only)]
  → Rationale: [one line — what will change and where]
  → Conflict: [none | ⚠️ Conflicts with [file] [section] — "[existing rule text]"]
  → Action: [replace | append | dismiss]   ← required for items with conflicts; defaults to "apply" if conflict==none

#2 — [language_code]: ...
  ...

Resolve in one line — for each item with a conflict, pick replace, append, or dismiss.
Example reply: `1=replace, 3=append, 5=dismiss`. Items not listed (or where conflict==none and unmentioned) apply as-written. Items marked Variables.csv flag-only cannot be applied (informational only).
```

## Step 6: Apply confirmed items (replace + dismiss; append is Step 5b)

Trigger the **Step 2 backup** now if not already triggered (this is the session's first write).

For each item in the routing set, in order:

1. **dismiss** → skip the item entirely. Acknowledge: `Item #N dismissed.`
2. **replace** OR **conflict==none (apply as-written)** → write a new entry to `corrections/corrections_log.json` > `corrections` array using the 8-field schema:

```json
{
  "language": "<code from item>",
  "notification_type": "<NOTIFICATION_TYPE from Step 1>",
  "issue_category": "<one of: grammar | tone | label | cultural | emoji | encoding | format — inferred from issue_text>",
  "original": "<the issue_text as submitted>",

}
```

**Multi-market split:** if Step 3 split an item into K markets (multi-language `Language:` line), write K entries — one per market. Each entry's `language` is a single string (per Phase 3 D-07).

**Confidence assignment ladder (Phase 3 D-08, unchanged):**
- `high`: user explicitly confirmed the correction OR it is a clear structural fact (empty translation, wrong variable for language, broken HTML tag).
- `medium`: correction is valid but context-dependent, involves linguistic nuance, or applies to tone/formality.
- `low`: speculative, needs native speaker verification, or inferred from ambiguous feedback.

3. **replace path — also delete or overwrite the conflicting prior entry.** When `replace` is chosen on a conflict against `corrections_log.json`: locate the conflicting entry by `language + issue_category + semantic match` and overwrite its fields with the new entry; do NOT add a duplicate row. When `replace` is chosen on a conflict against `label_patterns.json` or `tone_guidelines.json` or `variables_guide.md`: those config files are NOT edited at Tier 1 — only `corrections_log.json` is written, and the user's `replace` choice is interpreted as "let the new corrections_log entry stand alongside the existing config; the next promotion phase will reconcile." Note this behavior in the Step 6 output: `Note: config-file conflict on item #N kept at Tier 1 — config edit deferred to promotion phase.`

1. Read all entries in `corrections/corrections_log.json` > `corrections`.

   - No match: create a new rule entry:
     ```json
     {
       "rule": "<rule_extracted>",
       "language": "<code or 'all'>",
       "issue_category": "<category>",
       "occurrence_count": 1,
       "confidence": "<level>",
       "first_seen": "<date>",
       "last_seen": "<date>"
     }
     ```
3. Write the full file:
   ```json
   {
     "generated": "<today YYYY-MM-DD>",
     "total_rules": <N>,
     "rules": [ ... ]
   }
   ```

Run this rebuild **exactly once per session**, after all writes — never per-item.
