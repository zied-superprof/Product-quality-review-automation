{ "generated": "<ISO date>",

      "last_offered_at": "<ISO 8601 UTC>",

- not present in offers → offer

## Step 10: Promotion phase (FEEDBACK-08, FEEDBACK-09)

After Step 9 pruning, scan the surviving rules in `corrections/rules_summary.json` for Tier 1 → Tier 2 promotion candidates.

### 10.1 — Detect candidates and filter declined offers

For each rule in the freshly-pruned `rules_summary.json` > `rules`, evaluate the FEEDBACK-08 gate (ALL three must hold):

1. `occurrence_count >= 3`
2. `confidence == "high"`
3. No contradicting feedback in the last 30 days — scan `corrections/corrections_log.json` for any entry with the same `language` AND same `issue_category` AND an opposite verdict in `corrected` (e.g. one says "FALSE POSITIVE" and the other says "flag as error"), dated within `today - 30 days`.

Compute a deterministic `rule_id` for each surviving rule: `sha1(language + issue_category + rule)[:8]`.

Read `corrections/_promotion_offers.json` and apply the D-18 re-surface logic:
- If the rule_id is NOT in `offers` → keep as candidate.
- If `offers[rule_id].decision == "not_yet"` AND `current.occurrence_count > criteria_at_offer.occurrence_count` → keep as candidate (re-offer).
- If `offers[rule_id].decision == "not_yet"` AND counts match → suppress.
- If `offers[rule_id].decision == "never"` → suppress permanently.

If zero surviving candidates: output `Promotion: no candidates this session.` and proceed to Step 11 (Tier 3 advisory — Plan 13-06).

### 10.2 — Determine Tier 2 destination per candidate (D-11 routing tree)

For each surviving candidate, determine the destination(s):

1. **Variable-usage rule** — does the rule text reference a `@TPL_*@` variable name AND describe per-language behavior?
   - YES → destination is potentially TWO files: `config/label_patterns.json` (subject_variable_usage_rules.<VARIABLE_NAME>, machine-readable use_for/do_not_use_for/language_notes) AND `config/variables_guide.md` (the variable's H3 section, human-readable Valid for / Do NOT use for / Notes labels).
   - Claude drafts BOTH writes when the rule is per-language AND describes variable behavior. The user approves drafted text per file (independent approval — user may approve one and reject the other).

2. **Formality / tone rule** — does the rule text mention formality, register, address form, or tone? → destination: `config/tone_guidelines.json` (one of: `formality_rules.formal_vous_languages.languages`, `formality_rules.informal_standard_languages.languages`, `formality_rules.neutral_languages.languages`, `formality_rules.market_notes`, `brand_voice`, or `common_issues`).

3. **Other** — does the rule fit neither pattern (e.g. Arabic word order in CTAs, language-general phrasing, encoding/format rules)? → no Tier 2 destination matches. Output: `Candidate has no matching Tier 2 destination — stays in Tier 1; surface in Step 11 advisory if mechanically checkable.` Skip to next candidate; do NOT prompt the menu.

### 10.3 — One-by-one review (FEEDBACK-09)

Present each candidate (one with at least one matching destination) one at a time:

```
Promotion candidate (#N of M):
  Rule: "[rule text]"
  Language: [code]
  Issue category: [cat]
  Occurrence count: [n]    Confidence: [level]    Last seen: [date]
  Tier 2 destination(s): [list, e.g. "label_patterns.json + variables_guide.md" | "tone_guidelines.json"]

Action: promote | not yet | never | show full record
```

Behavior per choice:

- **promote** → proceed to Step 10.4 (drafted write flow).
- **not yet** → append entry to `corrections/_promotion_offers.json` > `offers`:
  ```json
  {
    "rule_id": "<id>",
    "last_offered_at": "<ISO 8601 UTC>",
    "decision": "not_yet",
    "criteria_at_offer": {
      "occurrence_count": <current>,
      "confidence": "high",
      "last_seen": "<current last_seen>"
    }
  }
  ```
  Increment `total_offers`. Acknowledge: `Deferred: rule will re-surface when occurrence_count > <current>.`
- **never** → append entry with `decision: "never"`. Increment `total_offers`. Acknowledge: `Locked at Tier 1: rule will not be offered again unless you manually edit corrections/_promotion_offers.json.`
- **show full record** → print the full rule object + the matching `corrections_log.json` entries (filtered by language + issue_category + semantic match), then re-prompt the menu.

### 10.4 — Drafted-write flow (on `promote`)

For each Tier 2 destination identified in Step 10.2:

1. Trigger Step 2 backup IF this destination is not yet backed up in this session (per-file backup-on-first-write — see CONTEXT.md "Mid-session new destination" Claude's Discretion bullet). Run:
   ```bash
   TS=$(date -u +%Y%m%dT%H%M%SZ)
   cp <dest_file> "corrections/backups/${TS}_$(basename <dest_file>)"
   ```

2. Draft the write text. The exact diff depends on destination:

   **For `label_patterns.json` > `subject_variable_usage_rules.<VARIABLE_NAME>`:**
   - If the variable already has an entry: propose adding the language code to `use_for` or `do_not_use_for` (whichever the rule indicates) and adding a `language_notes.<lang>` entry with the rule rationale.
   - If the variable does NOT yet have an entry: propose creating a new entry with `description`, `use_for`, `do_not_use_for`, `language_notes` populated from the rule.

   **For `tone_guidelines.json`:**
   - Formality classification rule: propose moving the language code between `formal_vous_languages.languages` / `informal_standard_languages.languages` / `neutral_languages.languages`, OR adding a `market_notes.<code>` entry.
   - Brand voice rule: propose appending a bullet to `brand_voice.core_principles`.
   - Recurring issue: propose appending a bullet to `common_issues`.

   **For `variables_guide.md` > `### \`@<VARIABLE_NAME>@\`` (the H3 section):**
   - Update one or more of the four labels: `**Purpose:**`, `**Valid for:**`, `**Do NOT use for:**`, `**Notes:**`.
   - For `**Valid for:**` / `**Do NOT use for:**`: add the language code to the list (or create the list if currently `_(BO-configurable; see Variables.csv for default)_`).
   - For `**Notes:**`: append a one-line note with the rule rationale.

3. Display the drafted write to the user:
   ```
   Drafted write for <destination_file>:
   ---
   <show the diff or the new/modified block in context>
   ---
   Approve this write? (yes / edit / skip)
   ```

4. Behavior per response:
   - **yes** → execute the write (Edit tool for JSON; Edit tool for markdown). Acknowledge: `Wrote: <destination_file>.`
   - **edit** → accept user-pasted replacement text, re-display, re-prompt. Loop until `yes` or `skip`.
   - **skip** → skip this destination only; continue with the next destination for the same candidate.

5. After all destinations for this candidate complete, proceed to the next candidate.

### 10.5 — Output promotion summary

After all candidates are processed:

```
Promotion phase complete:
- [N] candidates surfaced (after declined-offer filter)
- [P] promoted (writes: <list of destination files with counts>)
- [Y] deferred (not_yet)
- [V] locked (never)
- [S] no Tier 2 destination (stayed in Tier 1)
- corrections/_promotion_offers.json: <U> entries updated
```
